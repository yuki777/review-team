# コード品質の観点

正しく動くだけでなく、半年後に理解し変更できるかを検討する。局所的な名前の変更だけに留まらず、同じ挙動のまま分岐・状態・層を消せる「code judo」を探す。提案はレビューに留め、実装変更は行わない。

## 観点

1. **構造を減らす。** helper の追加や複雑さの移動より、経路・モード・状態を不要にできる表現を優先する。消せるものと、保存する挙動を説明する。
2. **ファイルの肥大化。** 1,000 行を跨ぐ変更は分割を検討する強い兆候。ただし行数だけで不具合としない。責務・読解経路の混線と、自然な分割境界を示す。全文がなければ総行数を推測しない。
3. **場当たり的な分岐。** 無関係な流れに挿入された特例や散在する条件は設計上の懸念。責務が明確な関数・状態遷移・モジュールで単純化できるか。ただし一つの if のために新しい層を作らない。
4. **平凡で直接的な実装。** 魔法的な動作、薄い wrapper、素通しの抽象、具体的データ形状を隠す汎用機構が理解を難しくしていないか。単純な名前付きデータ形状を優先する。
5. **型と境界。** 不要な optional、any、unknown、cast が契約の曖昧さを隠していないか。明確な入力検証とデータモデルで解消できるか。暗黙の fallback が不変条件を破っていないか。
6. **正本の責務。** 既存の helper を使わず重複していないか。機能固有の条件が共通層へ漏れたり、実装詳細が公開 API に漏れたりしていないか。既存の正しい置き場所を示すには packet 内の根拠が必要。
7. **調整と更新。** 独立作業の不要な直列化、途中で不整合になる関連更新に、明確な改善があるか。競合が起きる共有状態と、順序・原子性が必要な理由を示す。測定のない微小最適化は要求しない。

## 優先順位と判断の水準

構造の退行と大きな削減機会、分岐の混線、境界・型・肥大化、局所的な可読性の順に着目する。現在の意図、影響、変更コストに照らして問題を具体化する。

既存の実装より明らかに少ない構造で同じ契約を満たせるなら、具体案を率直に示す。ただし大規模な抽象化や好みの設計へ誘導するために問題を作らない。行数の閾値や「もっと綺麗」を自動的なブロッカーにはしない。

深刻な保守リスクを曖昧な言葉で薄めず、根拠と影響を示す。人格や能力への評価は不要。最終的な分類はリードが行う。
